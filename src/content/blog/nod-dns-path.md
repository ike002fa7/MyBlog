## 名字先变成地址

浏览器拿到域名后，会依次检查自身缓存、操作系统缓存和配置的递归解析器。递归解析器再根据需要访问根服务器、顶级域服务器和权威 DNS，最终得到可连接的地址。TTL 决定结果可以被缓存多久，也决定配置变更传播的速度。

## 地址不等于源站

启用 CDN 后，DNS 通常返回的是边缘节点地址。请求先到离访客较近的节点，节点根据缓存规则决定直接返回内容，还是回源获取新版本。静态博客因此可以获得较低延迟，也能减少源站压力。

## TLS 建立可信通道

HTTPS 连接需要协商协议与加密参数，并验证证书是否对应当前域名。证书只证明连接目标持有相应密钥，并不自动证明页面内容本身可靠。HSTS、现代 TLS 版本和正确的证书链共同减少降级与冒充风险。

## 调试要沿路径分层

遇到访问异常时，应按 DNS、网络连接、TLS、HTTP、缓存逐层排查。使用 `dig` 查看解析结果，用浏览器网络面板检查状态码与缓存头，再判断问题来自本地、边缘还是源站。分层思考比反复清缓存更接近问题本质。

## 递归解析与权威回答

递归解析器替用户寻找答案，权威服务器负责回答某个域名区域的最终记录。A 与 AAAA 指向 IPv4 和 IPv6 地址，CNAME 用于别名，MX 处理邮件，TXT 常用于域名验证与安全策略。不同记录承担不同职责，随意叠加会制造难以理解的依赖。

DNS 变更前降低 TTL，可以缩短切换期间旧答案的存活时间；变更稳定后再恢复较长 TTL，减少查询压力。但已经缓存的旧 TTL 不会因为配置修改立即消失，因此迁移必须预留传播窗口。

## HTTP 缓存是另一套系统

即使 DNS 已指向新节点，浏览器或 CDN 仍可能返回旧页面。`Cache-Control`、`ETag`、`Last-Modified` 和边缘缓存键共同决定内容是否复用。查询参数有时参与缓存键，有时会被平台忽略，不能把“加随机参数”当作普遍可靠的刷新方式。

调试时记录响应中的 `Age`、`Via`、`CF-Cache-Status` 等头部，可以判断响应来自浏览器、代理、边缘节点还是源站。DNS 正确而页面仍旧，问题通常已经进入 HTTP 缓存层。

## 建立访问路径图

为自己的域名记录注册商、权威 DNS、CDN、证书签发和源站托管关系。每层标注管理入口、恢复方式和到期风险。当访问中断时，这张小图比临时回忆所有平台账号更有价值。
